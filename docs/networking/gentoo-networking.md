## 1. Architecture Overview

Proxmox VE network management spans three layers:

```
┌──────────────────────────────────────────────────────────────────────┐
│  PVE Web UI / API  (/nodes/{node}/network, /cluster/sdn/*)           │
└────────────────────┬─────────────────────────────────────────────────┘
                     │ reads/writes
                     ▼
┌──────────────────────────────────────────────────────────────────────┐
│  /etc/network/interfaces           (PVE source-of-truth)             │
│  /etc/network/interfaces.d/sdn     (SDN overlay, auto-generated)     │
│                                                                      │
│  PVE Perl layer:                                                     │
│    PVE::INotify          — parses/writes /etc/network/interfaces     │
│    PVE::Network::SDN     — generates interfaces.d/sdn, FRR config   │
│    PVE::API2::Network    — REST API, calls pve-ifreload to apply     │
└────────────────────┬─────────────────────────────────────────────────┘
                     │ "apply" via pve-ifreload (Gentoo)
                     │         or ifreload -a (Debian)
                     ▼
┌──────────────────────────────────────────────────────────────────────┐
│  Gentoo Network Backend  (net-misc/pve-network-backend)              │
│                                                                      │
│  /usr/sbin/pve-ifreload                                              │
│    reads /etc/network/interfaces                                     │
│    translates to backend format                                      │
│    calls backend tool to apply                                       │
│                                                                      │
│  ┌─────────────────┐  ┌────────────────────┐  ┌──────────────────┐  │
│  │ systemd-networkd│  │  NetworkManager    │  │    netifrc       │  │
│  │ .network/.netdev│  │  nmcli keyfile     │  │ conf.d/net.pve   │  │
│  │ networkctl reload│  │  nmcli conn up     │  │ rc-service net.* │  │
│  └─────────────────┘  └────────────────────┘  └──────────────────┘  │
└──────────────────────────────────────────────────────────────────────┘
```

### What changed from upstream Proxmox

| Component | Upstream (Debian) | Gentoo port |
|---|---|---|
| Network apply tool | `ifreload -a` (ifupdown2) | `/usr/sbin/pve-ifreload` |
| Apply trigger | `PVE::API2::Network` PUT endpoint | Same, patched to prefer pve-ifreload |
| Host bridge config | `/etc/network/interfaces` applied by ifupdown2 | `/etc/network/interfaces` translated by pve-ifreload → backend |
| SDN overlay config | `/etc/network/interfaces.d/sdn` applied by ifupdown2 | Same file; parsed by pve-ifreload |
| ifupdown2 version check | `assert_ifupdown2_installed()` hard-dies without it | Patched to accept pve-ifreload as alternative |
| Boot-time bridge | ifupdown2 service applies on boot | Must configure backend to manage vmbr0 persistently |

## 2. /etc/network/interfaces on Gentoo

### Role of the file

`/etc/network/interfaces` is **kept as-is** in the Gentoo port. Its role:

| Operation | Uses this file? | Notes |
|---|---|---|
| PVE web UI displays network config | ✅ YES | `PVE::INotify::read_file('interfaces')` |
| PVE web UI saves network changes | ✅ YES | Written to `interfaces.new`, then renamed |
| PVE SDN reads bridge list for VxLAN | ✅ YES | Checks bridge exists before creating overlay |
| OS applies interface config on boot | ❌ NO | Backend config files are used instead |
| OS applies after "Apply Config" click | ✅ YES (via shim) | `pve-ifreload` reads it and translates |

### File format (subset PVE generates)

```
# Include SDN overlay (auto-generated by PVE when SDN zones are configured)
source /etc/network/interfaces.d/*

auto lo
iface lo inet loopback

# VM bridge — static IP
auto vmbr0
iface vmbr0 inet static
    address 192.168.1.10/24
    gateway 192.168.1.1
    bridge-ports enp3s0
    bridge-stp off
    bridge-fd 0

# Second bridge — DHCP (e.g. for storage/migration network)
auto vmbr1
iface vmbr1 inet dhcp
    bridge-ports enp4s0
    bridge-stp off
    bridge-fd 0
```

### Syntax supported by pve-ifreload

| Directive | Supported | Notes |
|---|---|---|
| `auto <iface>` | ✅ | Brings interface up on apply |
| `iface <iface> inet static` | ✅ | Static IPv4 |
| `iface <iface> inet dhcp` | ✅ | DHCP IPv4 |
| `iface <iface> inet manual` | ✅ | No address (bond/bridge members) |
| `address <CIDR>` | ✅ | CIDR notation required |
| `gateway <IP>` | ✅ | |
| `bridge-ports <port>` | ✅ | Linux bridge |
| `bridge-stp on\|off` | ✅ | Translated to STP setting |
| `bridge-fd <seconds>` | ✅ | Forward delay |
| `mtu <bytes>` | ✅ | |
| `source <glob>` | ✅ | Includes sub-files (e.g. `interfaces.d/*`) |
| `iface <iface> inet6 static` | ⚠️ PARTIAL | Parsed; networkd backend supports it |
| `bond-slaves`, `bond-mode` | ❌ | Not yet implemented |
| `ovs-type OVSBridge` | ❌ | OVS not supported in pve-ifreload |
| `pre-up`, `post-up`, `up`, `down` | ❌ | ifupdown2 hooks; ignored on Gentoo |
| `allow-hotplug` | ❌ | Ignored; use backend's hotplug mechanism |

## 3. Host Bridge Setup (vmbr0)

The VM bridge (`vmbr0`) must exist before `pvedaemon` starts, because:
- pvedaemon checks for bridge presence when listing/starting VMs
- Containers need `lxcbr0` or `vmbr0` for NAT networking

### 3.1 systemd-networkd (recommended for systemd systems)

Create two files **before first boot** (or in your cloud-init/kickstart):

**`/etc/systemd/network/10-vmbr0.netdev`**
```ini
[NetDev]
Name=vmbr0
Kind=bridge

[Bridge]
STP=no
ForwardDelaySec=0
```

**`/etc/systemd/network/20-vmbr0.network`**
```ini
[Match]
Name=vmbr0

[Network]
Address=192.168.1.10/24
Gateway=192.168.1.1
DNS=8.8.8.8
```

**`/etc/systemd/network/30-eth0-bridge.network`** (attach physical port)
```ini
[Match]
Name=enp3s0

[Network]
Bridge=vmbr0
```

Enable and start:
```bash
systemctl enable --now systemd-networkd
```

After first pve-ifreload run, these will be maintained automatically.

### 3.2 netifrc (OpenRC systems)

**`/etc/conf.d/net`**
```bash
# Source PVE-managed config (written by pve-ifreload)
source /etc/conf.d/net.pve

# Or configure vmbr0 directly here:
bridge_vmbr0="enp3s0"
config_vmbr0="192.168.1.10/24"
routes_vmbr0="default via 192.168.1.1"
bridge_forward_delay_vmbr0=0
brctl_vmbr0="setstp vmbr0 0"
```

Create init script symlink and add to boot:
```bash
ln -s /etc/init.d/net.lo /etc/init.d/net.vmbr0
rc-update add net.vmbr0 default
rc-service net.vmbr0 start
```

### 3.3 NetworkManager

```bash
# Create bridge
nmcli connection add type bridge con-name pve-vmbr0 ifname vmbr0 \
    bridge.stp no bridge.forward-delay 0

# Static IP
nmcli connection modify pve-vmbr0 \
    ipv4.method manual \
    ipv4.addresses 192.168.1.10/24 \
    ipv4.gateway 192.168.1.1

# Attach physical port
nmcli connection add type bridge-slave con-name pve-eth0-slave \
    ifname enp3s0 master vmbr0

nmcli connection up pve-vmbr0
```

After setup, pve-ifreload maintains the config on network changes.

## 4. Network Backends

### 4.1 Backend selection

`pve-ifreload` auto-detects the active backend:

```
systemd-networkd running → networkd backend
NetworkManager running   → nm backend
/etc/init.d/net.lo exists → netifrc backend
```

Force a specific backend:
```bash
PVENET_BACKEND=networkd pve-ifreload
PVENET_BACKEND=netifrc  pve-ifreload
```

### 4.2 systemd-networkd backend

- Writes to `/run/systemd/network/` (volatile — lost on reboot)
- Calls `networkctl reload` to apply
- **Important**: `/run/systemd/network/` is in tmpfs. Files survive until reboot.
  For persistent config, either:
  - Also write to `/etc/systemd/network/` (pve-ifreload only writes to /run)
  - Add a `pve-ifreload` call to a systemd `oneshot` service on boot

  Future improvement: `PVENET_NETWORKD_PERSISTENT=1` to write `/etc/systemd/network/`.

### 4.3 netifrc backend

- Writes `/etc/conf.d/net.pve` (persistent)
- Runs `rc-service net.<iface> restart` for each auto interface
- Requires `/etc/init.d/net.vmbr0` symlink to exist before first use
- SDN overlay interfaces (from `interfaces.d/sdn`) are parsed and added to `net.pve`

### 4.4 NetworkManager backend

- Creates/modifies connections named `pve-<iface>`
- Calls `nmcli connection up` for auto interfaces
- Persistent by default (NM stores connections in `/etc/NetworkManager/`)

## 5. SDN (Software-Defined Networking)

SDN overlay config is generated by `PVE::Network::SDN` into:
```
/etc/network/interfaces.d/sdn
```

This file contains Debian ifupdown2 stanzas for VxLAN/EVPN tunnel interfaces.
`pve-ifreload` reads it (via the `source /etc/network/interfaces.d/*` directive
in `/etc/network/interfaces`) and applies the tunnel interfaces.

### What works on Gentoo

| SDN type | Status | Notes |
|---|---|---|
| VLAN zones | ✅ | Kernel VLAN — works everywhere |
| VxLAN zones | ✅ | Kernel VXLAN — works everywhere |
| EVPN/BGP (via FRR) | ✅ | FRR is distro-agnostic |
| Simple zones | ✅ | Just Linux bridge, works |
| WireGuard fabrics | ✅ | Kernel WireGuard — works everywhere |
| IPAM (PVE built-in) | ✅ | Pure Perl, no OS dependency |
| DHCP (Dnsmasq) | ✅ | Dnsmasq available in Gentoo |
| DNS (PowerDNS) | ✅ | PowerDNS available in Gentoo |
| OVS (Open vSwitch) zones | ❌ | pve-ifreload doesn't translate OVS stanzas |
| QinQ zones | ⚠️ | Kernel supports it; pve-ifreload doesn't parse OVS stanzas |

### FRR (BGP/EVPN routing)

FRR is available in Gentoo as `net-misc/frr`. The SDN EVPN controller generates
`/etc/frr/frr.conf` and `/etc/frr/daemons`. Standard FRR management applies.

```bash
emerge net-misc/frr
rc-service frr start     # OpenRC
systemctl start frr      # systemd
```

## 6. Limitations and Behavior Differences

### Critical

| Issue | Impact | Workaround |
|---|---|---|
| **pve-ifreload writes to /run on networkd** | Bridge config lost on reboot | Manually write `/etc/systemd/network/` files for initial vmbr0 |
| **No bond support** | Cannot create bonded interfaces via PVE web UI | Create bonds manually; PVE can attach bridge to existing bond |
| **OVS not supported** | Cannot use Open vSwitch bridge type | Use Linux bridge (vmbr*) instead |
| **ifupdown2 hooks ignored** | `pre-up`, `post-up`, `up` hooks in interfaces file won't run | Implement in systemd units or OpenRC service scripts |

### Cosmetic / Minor

| Issue | Impact | Notes |
|---|---|---|
| **ifupdown2 version check** | Without patch, PVE UI shows "you need ifupdown2" error | Patched in pve-manager ebuild |
| **`ifreload -V` check** | Some PVE code checks ifupdown2 version string | Patched to accept pve-ifreload |
| **`interfaces.new` → `interfaces` rename** | PVE writes to `interfaces.new` first, renames on apply | pve-ifreload handles this correctly |
| **SDN `source` check** | PVE warns if `interfaces` lacks `source .../sdn` | pve-ifreload verifies this line exists |

### Network apply sequence on Gentoo

```
User clicks "Apply Configuration" in PVE web UI
  → PUT /nodes/{node}/network  (pvedaemon)
  → rename interfaces.new → interfaces  (if pending changes)
  → PVE::Network::SDN::generate_etc_network_config()  (writes interfaces.d/sdn)
  → PVE::Network::SDN::generate_dhcp_config()
  → /usr/sbin/pve-ifreload
      → detect_backend()  (networkd/nm/netifrc)
      → parse /etc/network/interfaces + interfaces.d/sdn
      → translate to backend format
      → apply via networkctl/nmcli/rc-service
  → PVE::Network::SDN::generate_frr_config()  (if EVPN in use)
```

## 7. Initial Setup Walkthrough

### Minimum configuration for a single-node Gentoo PVE host

```bash
# 1. Install pve-network-backend
emerge -av net-misc/pve-network-backend

# 2. Create /etc/network/interfaces
cp /usr/share/doc/pve-network-backend-1.0.0/interfaces.example /etc/network/interfaces
# Edit to match your interface name and IP:
nano /etc/network/interfaces

# 3. Create the bridge using your backend before starting PVE
# systemd-networkd example:
cat > /etc/systemd/network/10-vmbr0.netdev << 'EOF'
[NetDev]
Name=vmbr0
Kind=bridge
[Bridge]
STP=no
ForwardDelaySec=0
EOF
cat > /etc/systemd/network/20-vmbr0.network << 'EOF'
[Match]
Name=vmbr0
[Network]
Address=192.168.1.10/24
Gateway=192.168.1.1
EOF
# Attach your physical port (replace enp3s0):
cat > /etc/systemd/network/30-enp3s0-brport.network << 'EOF'
[Match]
Name=enp3s0
[Network]
Bridge=vmbr0
EOF
networkctl reload

# 4. Verify bridge is up
ip addr show vmbr0

# 5. Start Proxmox services
rc-service pve-cluster start    # OpenRC
rc-service pvedaemon start
rc-service pveproxy start
```

### After initial setup

From this point forward, network changes via the PVE web UI will:
1. Write updated config to `/etc/network/interfaces`
2. Run `/usr/sbin/pve-ifreload` to apply changes
3. Changes are reflected in the running network

## 8. Troubleshooting

### "you need ifupdown2 to reload network configuration"

The `pve-manager` patch has not been applied. Verify the pve-manager ebuild
includes `0001-gentoo-replace-ifreload-with-pve-ifreload.patch`.

Check: `grep -q pve-ifreload /usr/lib/perl5/vendor_perl/PVE/API2/Network.pm`

### vmbr0 disappears after reboot (networkd backend)

`pve-ifreload` writes to `/run/systemd/network/` which is volatile. Add a
persistent `.netdev`/`.network` file to `/etc/systemd/network/` for vmbr0.
Or add a boot service that runs `pve-ifreload` before `pvedaemon`.

### "net.vmbr0: init script not found" (netifrc backend)

```bash
ln -s /etc/init.d/net.lo /etc/init.d/net.vmbr0
rc-update add net.vmbr0 default
```

### SDN overlay doesn't apply

Check that `/etc/network/interfaces` contains:
```
source /etc/network/interfaces.d/*
```
Without this, pve-ifreload won't parse the SDN overlay file.

### "missing 'source /etc/network/interfaces.d/sdn' directive" warning in PVE

This warning comes from `PVE::Network::SDN`. It checks for a `source` line.
Ensure your `/etc/network/interfaces` has `source /etc/network/interfaces.d/*`
(glob is fine — PVE accepts it).

### Bridge not in PVE's interface list

PVE::INotify reads `/etc/network/interfaces` for its bridge list. The interface
**must** be defined there even if the backend actually manages it. If you created
the bridge manually via networkd/nmcli without adding it to `interfaces`, PVE
won't see it. Add a corresponding stanza to `/etc/network/interfaces`.
