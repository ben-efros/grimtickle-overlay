# 06 — cix-sources-7.3.1-r1: PCIe and Sky1 review

Review date: 2026-10-31.
Baseline: `linux-7.3.tar.xz` + `genpatches-7.3-2` (base + extras) + the
113-patch `files/7.3/` series (87 CIX vendor patches, `0150`-`0176`
local hardening), built and boot-tested on the reference Minisforum MS-R1.
Hardware: MS-R1 `P1WSB`, BIOS `1.0` dated 2026-04-29, 5× Sky1 PCIe root
ports (2× RTL8127 10GbE, 3× NVMe), ACPI boot (MCFG OEM ID `CIXTEK` /
`SKY1EDK2`).

This report is the 7.3.1 successor to the 7.2.9 audits (`01`-`05`). The
7.2.9 reports remain valid for the 7.2 lineage; several of their findings
were re-checked against the 7.3.1 vendor baseline and are noted below.

Terms: **fixed** = corrective patch added to `files/7.3/` in this round;
**documented** = evaluated, deliberately not changed, with rationale.

## 1. How the 7.3.1 PCIe stack is assembled

| Layer | Patch | Notes |
|---|---|---|
| Base kernel | Linux 7.3 | Already ships the *mainline* CIX Sky1 PCIe host driver `drivers/pci/controller/cadence/pci-sky1.c` (`CONFIG_PCI_SKY1_HOST`, OF-only) and the HPA cadence helpers |
| ACPI enumeration | `0030-disable-acpi-pcie-devices.patch` | Blocks `PNP0A08`, creates filtered platform devices for `CIXH2020` from the DSDT `_CRS`, binds the ACPI companion after registration, names them `sky1-pcie.N.auto` |
| Vendor host driver | `0031-add-cix-vendor-pci-driver.patch` | 2.6k-line `pci-sky1-cix.c` + debugfs; binds by `CIXH2020` ACPI HID |
| Cadence HPA rework | `0032-...fix-sky1-cix-vendor-pcie-driver.patch` | Renames the driver to `sky1-pcie-cix`, adds HPA ECAM region programming, `cdns_pcie_hpa_host_restore()`, capability-search helpers, syscore-API version gates |
| Clock lookup | `0035-pci-cadence-sky1-fix-clk-under-ACPI.patch` | Resolves `axi_clk`/`apb_clk`/`refclk_b` through `clk_get_sys(acpi_dev_name(adev), ...)` because CLKT clkdev entries are keyed by ACPI device name |
| Kconfig/module split | `0039-pci-cadence-add-PCI_SKY1_HOST_CIX-for-bsp-driver.patch` | `CONFIG_PCI_SKY1_HOST_CIX` (bool, ACPI + ARCH_CIX), one `pci-sky1-host-cix.o` object |
| Resource-name injection | `0007-soc-add-cix-acpi-resource-lookup-driver.patch` | `RSNL` DSDT table names the synthetic platform resources (`reg`, `rcsu`, `cfg`, `msg`, IRQ names). `pci-sky1-cix.c` **requires** these names via `platform_get_resource_byname()` |
| ASPM workaround | `0172-pci-cix-force-clock-pm-off-sky1-endpoints.patch` | RTL8127 `0x8127` ASPM/ClockPM disable on `CIXH2020` hosts |
| IOMMU | `0170-iommu-smmu-v3-sky1-pcie-bypass-ste.patch` | Sky1 PCIe bypass-STE/ATS override; also matters for PCIe DMA |

Two ACPI facts from the live board that the drivers depend on:

* `MCFG` OEM ID is `"CIXTEK"` / `"SKY1EDK2"`, matching the scan handler's
  detection (`pci-sky1-acpi.c:sky1_pcie_acpi_init()`).
* `CIXH2020` (`\_SB.PRC0`…`PRC4`) `_CRS` is `Memory32Fixed` register
  windows followed by `Interrupt`s and then the PCI windows/GpioIo/
  PinGroup descriptors. `0030` filters out all *address-space*
  descriptors, which keeps the `Memory32Fixed`/IRQ relative order used by
  `RSNL` indices 0-3 (`reg`, `rcsu`, `cfg`, `msg`). **This index
  coupling is an invariant**: changing the filter order/set breaks named
  resource lookup and PCIe probe.

## 2. Findings — PCIe

### P1 (high, fixed) — AER Root Command written to the wrong capability

`pci-sky1-cix.c:sky1_pcie_handle_rp_aer_irq()` reads the AER Root Command
from `reg_base + aer_offset + PCI_ERR_ROOT_COMMAND`, disables it, and then
re-enables it by writing to `reg_base + offset + PCI_ERR_ROOT_COMMAND`,
where `offset` is the **PCIe capability** offset (used for `DEVCTL`), not
the AER extended-capability offset. The re-enable write therefore lands
inside the PCIe capability/Link registers and leaves Root Command
interrupt enables cleared after the first AER interrupt — Root AER
reporting is permanently disabled for that port after one event.

Fixed by `0177-pci-sky1-cix-fix-aer-root-command-write-address.patch`.

### P2 (high, fixed) — `sky1_init_mutex` leaked on power-enable timeout

The x2/x1 branch of `sky1_pcie_set_pwr_en()` takes `sky1_init_mutex`,
then returns `-ETIMEDOUT` from inside the locked region if the
power-enable status poll fails. Every clock/reset/PHY/enumeration helper
takes the same mutex, so one PWR_EN timeout deadlocks all remaining
controller probes (and the suspend/resume paths) instead of failing that
controller.

Fixed by `0180-pci-sky1-cix-unlock-on-pwren-timeout.patch`.

### P3 (medium, fixed) — NULL dereference in endpoint lookup

`sky1_pcie_get_ep_pci_dev()` walks `bridge->bus->children` and then
`root_bus->devices` without checking either pointer. It is called from
the PME work item and both AER interrupt paths, including while the link
is down/after endpoint removal, where `bridge->bus` can be unset and no
child bus can exist. A NULL `bridge->bus` or `root_bus` is a kernel
NULL-pointer dereference in interrupt/work context.

Fixed by `0178-pci-sky1-cix-guard-ep-lookup-against-missing-bus.patch`.

### P4 (medium, fixed) — two of three AER IRQ requests unchecked

`sky1_pcie_request_irq()` calls `devm_request_threaded_irq()` for the
correctable, fatal and non-fatal AER lines but only checks the third
return value. A failure for `pcie-aer-c`/`pcie-aer-f` is discarded and
probe continues without those handlers.

Fixed by `0179-pci-sky1-cix-check-each-aer-irq-request.patch`.

### P5 (medium, fixed) — clock lookup errors discarded

`sky1_pcie_parse_clocks()` stores `PTR_ERR()` in `ret`, continues, and
returns 0; a failed required `axi_clk`/`apb_clk`/`refclk_b` therefore
leaves `ERR_PTR()` clocks in `struct sky1_pcie`, later handed to
`clk_prepare_enable()`. The ACPI path also sets the clock pointer even
when the lookup failed. This is a latent crash/half-initialised
controller on any board where one of these clocks is missing or not yet
registered.

Fixed by `0181-pci-sky1-cix-propagate-clk-lookup-failures.patch`; the
optional `refclk_b` `-ENOENT` case still degrades to `NULL`.

### P6 (medium, fixed) — synthetic device name collides with mainline driver

`0030` names the platform devices it creates `"sky1-pcie"`. Linux 7.3 now
ships the mainline host driver `pci-sky1.c` with driver name
`"sky1-pcie"` and `PROBE_PREFER_ASYNCHRONOUS`. `platform_match()` falls
back to comparing `pdev->name` with `drv->name`, so the mainline driver
can bind these ACPI-created devices before/while the vendor
`sky1-pcie-cix` driver probes. The mainline probe then fails on the
DT-only named resources (`-ENODEV`), and if `RSNL` naming has already run
it could partially claim the same controller. On the 7.3.1 test boot the
vendor driver won, but the successful binding currently depends on
initcall/probe ordering rather than on a real match.

Fixed by `0184-pci-sky1-acpi-name-pdev-after-vendor-driver.patch`, which
names the devices `"sky1-pcie-cix"` to match the vendor driver (the ACPI
HID match is unaffected).

### P7 (medium, fixed) — gpio-cadence IRQ mask writes not width-limited

`0017-gpio-add-acpi-support-to-cadence-driver.patch` writes
`~saved_regs.irq_en` to `CDNS_GPIO_IRQ_EN`, and `~wake_active` to
`CDNS_GPIO_IRQ_DIS` on suspend/shutdown, without masking to the
implemented GPIO count. The live MS-R1 exposes banks with 10 and 17
GPIOs, not just 32. Armbian's CIX 6.18 tree carries the same fix
(`2001-gpio-gpio-cadence-fix-crashing-pcie-on-cix-p1-acpi-s.patch`).

Fixed (width part only) by
`0182-gpio-cadence-mask-irq-writes-to-implemented-width.patch`.

### P8 (low, fixed) — wrong `pcie_x2_rc` strap/status addresses in DT

`arch/arm64/boot/dts/cix/sky1.dtsi` uses `0x0a0600340`/`0x0a0600440`
(extra hex digit) for `pcie_x2_rc` `rcsu_strap`/`rcsu_status`. ACPI boot
does not consume these, but DT boot maps the wrong window. Same fix as
Armbian `uefi-arm64-dt-7.3/1001`.

Fixed by `0183-arm64-dts-cix-fix-sky1-pcie-x2-rcsu-addresses.patch`.

### P9 (low, documented) — optional regulator errors masked

`sky1_pcie_parse_ep_pwr_supply()` uses
`devm_regulator_get_optional()` and turns *every* error into "no
regulator", including `-EPROBE_DEFER` from a real supplier. The MS-R1
DSDT does not expose `vcc-pcie`/`wlan-en` suppliers, so this is inert on
the reference board; on a board where the supplier probes later the
controller could be initialised without its rail. Recommend handling
`-EPROBE_DEFER` specially if such a board appears; not patched to avoid
untestable behaviour changes.

### P10 (low, documented) — `of_property_read_bool()` on the ACPI path

`sky1_pcie_parse_aer_irq()` reads `sky1,aer-uncor-panic` with
`of_property_read_bool(pdev->dev.of_node, ...)`, which is always false
under ACPI. The MS-R1 `_DSD` sets it to 0 anyway, so behaviour is
correct; if firmware ever wants panic-on-uncorrectable-AER under ACPI the
property would be ignored. Not patched (panic policy is deliberately
conservative).

### P11 (info) — hard-coded PCI domain

`devm_acpi_pci_bridge_init()` sets `bridge->domain_nr = 0` with a TODO
for `_SEG`. MS-R1 is a single-segment system (`_SEG = 0` for all five
root ports), so this is correct today; multi-segment CIX firmware would
need `_SEG` support.

### P12 (info) — shared Cadence HPA changes

`0032` changes shared files (`pcie-cadence-host-common.c`,
`pcie-cadence-host-hpa.c`, `pcie-cadence.c`) used by the mainline
`pci-sky1.c` and other Cadence host drivers. The changes are additive
(new HPA helpers, an ECAM region builder, `device_property_*` instead of
`of_property_*` in `cdns_pcie_host_map_dma_ranges()`, vendor/device-id
fallback). They compile cleanly against 7.3.1, and the MS-R1 ACPI path
exercises the new HPA helpers; no regression was observed on the
non-Sky1 compile paths, but the change deserves upstream scrutiny before
carrying it in a general-purpose kernel.

## 3. Findings — Sky1 platform (non-PCIe)

Reviewed at two depths: boot-critical/ACPI-ordering patches were read in
full; peripheral patches were reviewed for API/ABI drift and for
regressions already found in the 7.2.9 audits.

### S1 — panthor 7.3 vendor series supersedes the 7.2.9 boot-risk findings

The 7.2.9 `05-boot-risk.md` F1/F2 concerns (ACPI PowerResource vs
raw-SMC GPU power-on, `_CCA`-based coherency) were caused by the 7.2.9
*srcshelton* panthor rework. CIX's 7.3 vendor series `00111`-`00116`
replaces that with the vendor's own ACPI bring-up, SCMI DVFS and
coherency rework. The 7.3.1 test boot reached panthor probe
(`Using ACE-Lite bus coherency (Sky1)`) without an SError; see the boot
log in `07-decisions-7.3.1-r1.md`.

### S2 — PDC Kconfig is enabled on every ARM64 GIC kernel

`0012-irqchip-add-cix-sky1-pdc-driver.patch` declares
`config SKY1_PDC bool; depends on ARM_GIC; default y`. That builds the
Sky1 wake-up irqchip into every arm64 GIC kernel using this patch set,
not just CIX systems. It is inert without a matching `cix,sky1-pdc` DT
node or `CIXHA019` ACPI device, but should be `default y if ARCH_CIX`
(or `depends on ARCH_CIX || COMPILE_TEST`). Documented, not patched
(Kconfig-only, no runtime effect on MS-R1).

### S3 — pinctrl `dt_node_to_map()` publishes `*map` before a failing check

`0048-pinctrl-sky1-add-acpi-support.patch` assigns `*map = new_map` and
`*num_maps` before `of_get_parent(np)`; if the parent is missing it
`kfree(new_map)`s and returns while `*map` still points at freed memory.
This is the DT path only; the MS-R1 ACPI config does **not** enable
`PINCTRL_SKY1` (GPIO goes through `gpio-cadence`), so it is not reachable
on the reference board. Documented for an eventual DT user.

### S4 — Sky1 GPT timer still discards `-EPROBE_DEFER` for its IRQ

`0173-clocksource-sky1-defer-on-missing-timer-clocks.patch` correctly
preserves `-EPROBE_DEFER` for the two clocks, but
`sky1_timer_probe()` still turns a deferred IRQ mapping
(`platform_get_irq()` < 0) into `-EINVAL`. On the MS-R1 the IRQ is
already mapped before the timer probes, so the timer works; the same
class of bug would bite a platform whose PDC/IRQ mapping is later.
Documented, not patched (the 0173 change already covers the observed
failure).

### S5 — mailbox ACPI property spelling is inconsistent

`0001-mailbox-add-acpi-support-to-cix-mailbox-driver.patch` reads
`cix,mbox_dir` under ACPI and `cix,mbox-dir` under DT. It matches the
MS-R1 DSDT (`cix,mbox_dir`), but the asymmetry is a future trap for
firmware/DT authors; no functional issue on the reference board.

### S6 — USB/PHY hardening remains the area with the most local patches

`0150`-`0162`, `0176` (`cix` PHY/USB, rts5453, cdnsp-sky1) are local
hardening on top of CIX's 7.3 USB work. They are independent of the PCIe
findings above; the 7.3.1 test boot enumerated xHCI, the RTS5453 PD
controller and the two `cdnsp-sky1` controllers without the SErrors seen
in earlier rounds. The deferred `.deferred` patches (`0159`, xhci ACPI
LPM autodetect) remain intentionally unapplied.

### S7 — remaining peripheral families

`00100`/`00101`/`00102` (display), `00111`-`00116` (panthor), `0013`/
`0021`/`00220`-`00222` (audio), `0024`-`0027` (USB/PHY), `0028`/`0044`
(PWM), `0033`/`0165` (regulator), `0042`/`0051`/`0052`/`0063`/`0064`
(thermal), `0045`/`0173` (timer), `0048` (pinctrl), `0049` (RTC),
`0050` (DMI/model), `0055` (SBSA watchdog), `00052`-`00062` (clocks/
resets), `0007`/`0008`/`0041`/`0175` (ACPI/genpd/CLKT) were reviewed
against 7.3 API/ABI drift and against the boot log. No new compile-time
or boot-time defect was identified beyond S2-S5; the 7.3.1 boot test is
the end-to-end check for this family.

## 4. What was tested

* Full 115-patch chain applies to a pristine `linux-7.3` + `genpatches-7.3-2`
  tree with zero rejects (local and on the MS-R1).
* 7.3.1 kernel built on the MS-R1 (native aarch64 GCC 16.2) with the
  patched PCIe/gpio/DT files; see `07-decisions-7.3.1-r1.md` for the final
  build/boot result and the PCIe/Sky1 evidence collected.
* Running 7.1.5 baseline collected first (dmesg, `lspci -vvv`, ACPI
  DSDT/SSDT disassembly, `/proc/config.gz`, `/proc/iomem`, GPIO state) to
  have a known-good reference for the ACPI/resource-name invariants above.

## 5. Confidence and limits

* P1/P2/P4/P5 are unambiguous code defects with direct evidence in the
  applied source; P3/P6/P7/P8 are ordering/robustness fixes whose
  practical impact depends on timing/hardware and are adopted because the
  change is strictly safer.
* AER-error *recovery* behaviour (as opposed to interrupt-enable state)
  was not exercised on hardware: no PCIe errors were injected. The
  fixes are static-analysis/scope driven.
* NPU/VPU userspace was not tested (no UMD in the reference image); the
  ms-r1-npu-hack evaluation is in `07-decisions-7.3.1-r1.md`.
